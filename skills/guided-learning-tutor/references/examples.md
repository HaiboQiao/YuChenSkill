# 完整教学案例与验证点

这些是实际生成的测试回答，供开发和复核；普通教学不加载案例全集。案例只示范组织方式，不能当作固定回复模板。Case 5 承接 Case 2；Case 10 的前文是“我理解把前面的数累加起来，但区间公式和下标还不够稳”。

## Case 1

验证重点：Quick：职责区别，不展开 Shell 历史。

用户：Bash 是什么？和终端有什么区别？

助手：

Bash 是一个接收、理解并执行文字命令的程序。终端是你输入这些命令、看到执行结果的界面；Bash 可以运行在这个界面里。你看到的是同一个窗口，但“负责显示”和“负责理解命令”是两件事。

比如，在运行 Bash 的终端里输入：

```bash
echo "你好"
```

过程是：终端把你输入的文字交给 Bash → Bash 识别 `echo`，执行“输出文字”这个命令 → 终端显示 `你好`。

负责解释命令、让你与操作系统交互的这类程序叫 **Shell**，中文常叫“命令解释器”；Bash 是其中一种，全称是 Bourne Again SHell。你也可能在同一个终端里使用 PowerShell 或其他 Shell。

因此，换一个终端窗口，不一定换了 Bash；换成 PowerShell，也不一定要换终端应用。终端像交流的窗口，Bash 像窗口背后负责理解命令的人，这个比喻只用于区分两者的职责。

记住两点就够了：**终端负责输入和显示，Bash 负责解释和执行命令。** Bash 还能执行写在文件里的一串命令，所以它也常用于写脚本。

Bash 的定义及上述 `echo` 行为依据 [GNU Bash 官方手册](https://www.gnu.org/software/bash/manual/html_node/What-is-Bash_003f.html)与 [Bash 内置命令说明](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html)。

## Case 2

验证重点：Standard：需求、抵消机制、小数据与代码。

用户：给我讲讲前缀和。

助手：

前缀和就是先把“从开头加到各个位置的结果”存起来。以后想知道中间一段的总和，就用两个已经存好的结果相减。它特别适合这样的问题：一组数字基本不变，但你要反复查询不同区间的和。

假设每天的收入是：

```text
数字：       3    2    5    1
下标：       0    1    2    3
```

如果你问下标 1 到下标 2 的收入，就是 `2 + 5 = 7`。偶尔问一次，直接加就行；但如果问很多次，每次重新加，就会反复处理相同的数字。

我们先做一遍累计计算，把这些结果存下来：

```text
取前几个数： 0    1    2    3    4
累计总和：   0    3    5   10   11
```

下面把这个新数组叫 `prefix`。注意它比原数组多一项：`prefix[0] = 0`，表示一个数都不取；`prefix[3] = 10`，表示取前三个数，也就是 `3 + 2 + 5`。这里索引表示的是“取几个数”，不要和原数组里“某个数的位置”混在一起。

现在求下标 1 到 2 的和：

```text
前三个数的和： 3 + 2 + 5 = 10
前一个数的和： 3         =  3
相减：            2 + 5 =  7
```

**相减删掉了我们不想要的开头，留下的恰好是目标区间。**

把这个例子写成通用规则：原数组下标从 0 开始，查询 `l` 到 `r`，左右两端都包含在内，那么：

```text
区间和 = prefix[r + 1] - prefix[l]
```

为什么右边要 `+1`？因为下标为 `r` 的数，是第 `r + 1` 个数，必须把它包含进累计结果。为什么减 `prefix[l]`？因为它包含的恰好是目标区间之前的 `l` 个数。

对应的 Python 示例：

```python
numbers = [3, 2, 5, 1]

prefix = [0]
for number in numbers:
    prefix.append(prefix[-1] + number)

l, r = 1, 2
answer = prefix[r + 1] - prefix[l]
print(answer)  # 7
```

循环里每读到一个数，就把它加到上一次的累计结果上。因此 `prefix` 依次变成 `[0, 3]`、`[0, 3, 5]`，最后是 `[0, 3, 5, 10, 11]`。

先准备这些累计结果，要把 `n` 个数各处理一次，记作时间复杂度 `O(n)`；之后每次查询只取两个值、减一次，不随区间变长而增加工作，记作 `O(1)`。代价是多存一个长度为 `n + 1` 的数组。若只查询一次，直接求和通常就够了；若原数组经常改动，已存的累计结果也会受影响。

先抓住两个关键点：`prefix[k]` 表示前 `k` 个数的和；查询一段时，用“包含目标段的累计和”减掉“目标段之前的累计和”。公式是这两句话的结果。

## Case 3

验证重点：Review：升序数组和候选区间定义，只修循环条件混淆。独立复测后的最终回答。

用户：二分我基本会，但是 left < right 和 left <= right 总搞混。

助手：

你混淆的关键，是把循环条件当成了可以单独背的模板。先看 `left`、`right` 表示哪些位置，再问：只剩一个候选位置时，要不要进循环检查它？要检查，就让循环继续；如果循环只是为了把范围缩到一个位置，就可以停下来，最后处理它。

先对照两种“在升序数组中查找某个值，找到就返回”的写法。设数组长度为 `n`，下标从 `0` 开始：

| 尚未排除的位置 | 初始边界 | 循环条件 |
|---|---|---|
| 从 `left` 到 `right`，两端都包含 | `left = 0, right = n - 1` | `left <= right` |
| 从 `left` 到 `right` 前一个位置，不包含 `right` | `left = 0, right = n` | `left < right` |

原因就在最后一个候选：第一种的 `left == right` 表示**还剩一个位置**；第二种的 `left == right` 表示**已经没有位置**。

例如在 `[3, 6, 9]` 中找 `9`。中间的 `6` 太小，排除它及左侧后，都把 `left` 移到下标 `2`：

- 两端包含时，剩下 `[2, 2]`。必须再检查下标 `2`，所以要允许 `left == right` 进入循环。
- 不包含右端时，剩下 `[2, 3)`，也只有下标 `2`，此时 `2 < 3`，仍会进入循环。

边界更新也必须配套：排除 `mid` 及右侧时，第一种用 `right = mid - 1`，第二种用 `right = mid`，因为第二种的右端本来就不算候选。排除 `mid` 及左侧时，两种都用 `left = mid + 1`。

还有一种你可能见过的 `left < right`：左右两端都包含，但循环的任务是**缩到唯一候选**，停下后再检查或返回 `left`。因此不能简单记成“两端包含就一定用 `<=`”。

记住这个判断顺序就够了：**边界包含谁 → 相等时还剩什么 → 最后一个候选在循环内处理，还是循环后处理。** 循环条件、边界更新和结束后的处理是一套，不能只换 `<` 或 `<=`。

## Case 4

验证重点：Deep：学习地图后只展开树的结构。

用户：给我详细讲一下树。

助手：

这里先按编程中的“树”来讲：它是一种把数据组织成层级关系的结构，适合表达目录、组织关系和分类。它的关键特征是各个部分连在一起，而且沿连接关系走，不会绕一圈回到原处。树的内容很多，本轮先把“它为什么是一棵树，以及怎样读懂它的结构”讲透。

后续可以沿这条路径学：

1. 树的结构：谁与谁相连，谁在谁下面。本轮讲这一块。
2. 深度和高度：描述一个位置离顶部多远，以及下面还有多少层。
3. 遍历：按照一种规则，把树里的数据逐个访问。
4. 二叉树：每个位置最多有两个直接下级，许多常见算法围绕它展开。
5. 二叉搜索树：在二叉树上加上大小顺序，让寻找数据更有方向。

先看一棵小树：

```text
       A
      / \
     B   C
    / \
   D   E
```

这里每一个字母代表一个存放数据的位置，叫**节点**；字母之间的连接叫**边**。图中的斜线只表示连接关系，并不表示数据必须画在某个方向上。节点可以存数字、文件名，也可以存一条记录。

为什么说这张图是树？因为从任何一个节点，都能沿连接走到其他节点；同时，没有一条不重复走边的路线，能兜一圈回到起点。更正式地说，一棵非空的普通树，是“连通且没有环”的图：连通就是各处互相能到达，环就是兜圈的连接。记住这两个直观意思，比先背定义更有用。

它带来一个很重要的结果：**任意两个节点之间，只有一条不绕路、不重复节点的路径。**

比如从 D 到 C，只能走 `D → B → A → C`。如果再添加一条 D 与 C 的连接，那么从 D 到 C 就有两条路线，而且可以绕成 `D → B → A → C → D` 的圈；这时整个结构就不再是普通树。后面很多树的算法敢于沿一条路线处理，正是依赖这种结构。

要表达“上下级”，我们还需要选一个起点。图里把 A 选作最上面的起点，叫**根节点**。从 A 出发读这棵树，B 和 C 就在 A 的下一层，D 和 E 又在 B 的下一层。这里的“上”和“下”是组织关系，和屏幕上实际画的位置没有必然关系。

对于直接相连的上下级，上面的叫**父节点**，下面的叫**子节点**。所以：

- A 的子节点是 B、C。
- B 的子节点是 D、E。
- D 的父节点是 B，不能把 A 叫作 D 的父节点。

最后一点容易混：A 虽然在 D 的上方，却隔了一层。沿父节点不断向上到达的节点统称为祖先；因此 B、A 都是 D 的祖先，但只有 B 是它的直接父节点。父子强调“直接相邻”，祖先强调“沿层级往上”。

选定根之后，每个非根节点都恰好有一个父节点。这不是随便规定出来的：从它走向根的路径只有一条，路径上紧挨着它的上一个节点，就是它的父节点。根没有父节点；一个节点可以有多个子节点。

再看最下方的 D、E、C：它们没有子节点，这种节点叫**叶子节点**。请注意，C 虽然没有画在和 D、E 一样低的位置，也是叶子。判断叶子看的是“有没有子节点”，不是看图上它排得有多低。一个只有根的树里，根同时也是叶子。

最后把 B 单独拿出来，连同它下面的 D、E 一起看：

```text
     B
    / \
   D   E
```

它自己也形成了一棵树，叫“以 B 为根的子树”。这里不能随便挑几个节点就说是 B 的子树：在这种常用说法里，需要包含 B，以及它下面的所有后代。这个性质很有用——大树下面仍然是同样结构的小树，所以许多树的问题能分成“处理当前节点”和“处理它下面的小树”。具体算法等讲遍历时再接上。

还能用一个数量关系检验直觉：普通树有 `n` 个节点时，恰好有 `n - 1` 条边。单独一个节点不需要边；以后每接入一个新节点，用一条边把它接上，就能保持连通。如果多接一条边，把已经连通的两个位置再次连起来，就会出现圈。上图有 5 个节点、4 条边，正符合这个关系；不过只数边不够，还要确认整体连通。

这一轮先把结构读明白：连接不成圈；选定根后形成上下级；父子是直接关系；没有子节点的是叶子；一个节点连同它的所有后代构成一棵子树。下一层学深度和高度时，只是在这个已看清的结构上数距离。

## Case 5

用户：还是没看懂。

我们先把公式和代码放下，只看一个动作：**从一笔总数里，减掉前面不要的部分。** 前缀和利用的就是这件事。

假设你每天赚的钱是：

```text
第 1 天：3 元
第 2 天：2 元
第 3 天：5 元
```

现在想知道“第 2 天和第 3 天，一共赚了多少”。

你手上已经有两张累计账单：

```text
到第 3 天为止：3 + 2 + 5 = 10 元
到第 1 天为止：3         =  3 元
```

```text
10 - 3 = 7 元
```

## Case 6

验证重点：Learn by Doing：使用目的、历史示意、只读第一步，不实际执行 Git。

用户：教我 Git rebase。

助手：

`git rebase` 的作用，是把你这条分支上的一串提交，重新接到另一个起点后面。比如你开始做功能时主分支还停在 A，后来主分支更新到 C，你可以把自己的修改重新应用到 C 后面。先理解它改变了什么，再做第一步检查。

这里“提交”指 Git 保存的一次修改记录；“分支”可以先理解成指向一串提交最新位置的名字。假设你自己的分支叫 `feature`，主分支叫 `main`：

```text
原来：
A──B──C       main
 \
  D──E        feature

把 feature 接到 C 后面以后：
A──B──C──D'──E'
      ↑      ↑
     main  feature
```

Git 会尝试把 D、E 里的修改依次应用到 C 后面。图里写成 D'、E'，因为它们是重新生成的提交，提交标识通常会变化；`main` 本身不会因此向前移动。这个机制依据 [Git 官方 rebase 文档](https://git-scm.com/docs/git-rebase)。

因此实操前需要知道：这是不是你自己正在用的分支，是否有还没保存成提交的修改。已经被别人拿来继续工作的共享分支，不能随手这样改历史；否则别人还基于旧的 D、E 工作，而你这里已经换成 D'、E'。

我们先只做一个查看动作。在你想练习的 Git 仓库目录里运行：

```bash
git status
```

它的目的，是确认当前所在分支，以及有没有尚未提交的修改；这条命令不会进行 rebase。

预期会看到当前分支名，以及类似“工作区干净”，或者哪些文件已修改、未跟踪的提示。把这段结果贴给我，我们根据你实际所在的分支和修改状态，接着选正确的起点。现在先不改提交历史。

## Case 8

验证重点：Non-trigger：交付脚本，避免强加教学。

用户：帮我写一个 Python 文件读取脚本。

助手：

下面的脚本读取你指定的 UTF-8 文本文件，并把完整内容输出到终端。保存为 `read_file.py`：

```python
import sys

if len(sys.argv) != 2:
    print('用法：python read_file.py "文件路径"', file=sys.stderr)
    sys.exit(2)

try:
    with open(sys.argv[1], "r", encoding="utf-8") as file:
        content = file.read()
except UnicodeDecodeError:
    print("读取失败：文件不是有效的 UTF-8 文本。", file=sys.stderr)
    sys.exit(1)
except OSError as error:
    print(f"读取失败：{error}", file=sys.stderr)
    sys.exit(1)

sys.stdout.write(content)
```

运行示例：

```bash
python read_file.py "D:\资料\笔记.txt"
```

把示例路径换成实际文件路径即可。这个版本一次读取整个文件，适合普通大小的文本文件。

## Case 9

验证重点：任务兼教学：完整脚本及原因，区分文本显示与字节保留。独立复测后的最终回答。

用户：帮我写一个 Python 文件读取脚本，但我想知道每一步为什么这样写。

助手：

下面先按“读取 UTF-8 编码的文本文件，并把内容显示出来”来写。整个过程是：指定文件 → 打开文件 → 读出文字 → 关闭文件 → 显示文字；下面的脚本可以保存为 `read_file.py`。

```python
file_path = "notes.txt"

try:
    with open(file_path, "r", encoding="utf-8") as file:
        content = file.read()

    print(content)

except FileNotFoundError:
    print(f"找不到文件：{file_path}，请检查文件名和位置。")

except UnicodeDecodeError:
    print("文件无法按 UTF-8 读取，请确认它的实际编码。")
```

每一步为什么这样写：

1. **`file_path = "notes.txt"`：先确定要读哪个文件。** 把文件名单独放在一个变量里，以后换文件只改这一行。这里的相对路径从“运行脚本时的当前目录”开始找，并不一定是脚本所在的文件夹。也可以写绝对路径，例如 `file_path = r"D:\资料\notes.txt"`；前面的 `r` 让反斜杠按路径字符处理。

2. **`with open(...) as file`：打开文件，并安排好关闭。** `"r"` 表示只读取文件；`encoding="utf-8"` 告诉 Python 如何把文件里的数据转换成文字，这个转换规则叫“编码”。指定它，是为了不依赖不同电脑的默认规则。`file` 是打开后用于读取的对象。使用 `with`，离开缩进范围时就会自动关闭文件，即使读取过程中出错也会关闭，因此不用自己补一条关闭语句。

3. **`content = file.read()`：把文件中的全部文字读出来。** 打开文件只是建立读取入口，真正取出内容的是 `read()`。读出的结果是一段字符串，保存在 `content` 中。它必须写在 `with` 的缩进范围里，因为离开这个范围后文件就已经关闭了。这里一次读取全部内容，适合普通的小文本文件。

4. **`print(content)`：显示已经读出的文字。** 它放在 `with` 外面，是因为此时内容已经留在变量里，显示它不再需要文件保持打开。`print` 显示完还会额外加一个换行。

外层的 `try` 表示“尝试执行这段操作”；两个 `except` 分别处理文件不存在、文件不能按 UTF-8 解读的情况，让常见问题显示成容易理解的提示。遇到编码提示时，应确认文件实际使用的编码，不要直接忽略错误，以免丢失文字。

例如，当前目录里有一个 UTF-8 的 `notes.txt`，内容是：

```text

```

运行脚本后就会显示这两行。这个脚本读取的是文本：读取时会进行文字转换，并可能把不同形式的换行统一为 `\n`，所以它不适合需要逐字节保持原样的图片、音频等文件。

## Case 10

验证重点：Deep：上下文已懂累计；聚焦公式与边界，其余模块延后。

用户：这个知识我要彻底学透。

助手：

你已经理解累计求和，我们直接往下走：把“累计结果为什么能相减，以及公式为什么不会多算少算”讲透。前缀和真正容易出错的地方，是累计数组的下标代表什么。只要把这个含义固定下来，公式、边界和代码就能从同一个规则推出来。

整体学习路径可以分成四块：

1. 区间相减与下标边界：把查询公式推出来，本轮聚焦这里。
2. 适用条件与代价：判断什么情况下值得提前计算，数据变化后会发生什么。
3. 用累计结果寻找区间：把“查询一段”推进到“寻找符合条件的一段”。
4. 二维前缀和：把一条线上的求和推广到矩形区域。

先不展开后面三块。当前模块只需要统一一件事：**`prefix[k]` 表示原数组前 `k` 个数的和。**

这句话里，`k` 是数量。原数组的下标则从 0 开始，表示位置。我们用一组含负数的数组，避免把累计结果误以为一定越来越大：

```text
原数组 a：      4   -1    3    2
元素下标：      0    1    2    3

k：             0    1    2    3    4
prefix[k]：     0    4    3    6    8
```

你已经会累计求和，这里无需再练加法。只检查含义：`prefix[2] = 3`，存的是前两个数 `4 + (-1)`，没有包含下标 2 的 `3`；`prefix[3] = 6` 才把它包含进去。零开头的下标与“第几个”相差 1，这就是公式里 `+1` 的来源。

现在查询下标 1 到 2 的总和，两端都要包含，也就是 `-1 + 3`。

我们需要一个累计结果覆盖到下标 2：这意味着取前 3 个数，所以选择 `prefix[3]`。但它多带了下标 0 的 `4`；这部分正好是前 1 个数，所以减掉 `prefix[1]`：

```text
prefix[3] = 4 + (-1) + 3
prefix[1] = 4

相减得到：    (-1) + 3 = 2
```

相减能奏效的原因不是数字碰巧合适，而是两份累计结果中都有同一段开头。减法把那段公共部分抵消了。

把这个推理写得一般一点。查询 `a[l]` 到 `a[r]`，假设 `0 <= l <= r < n`，`n` 是数组长度。为了覆盖最后的 `a[r]`，第一份累计和必须包含前 `r + 1` 个数：

```text
prefix[r + 1] = a[0] + ... + a[l - 1] + a[l] + ... + a[r]
prefix[l]     = a[0] + ... + a[l - 1]
```

把相同的开头减掉，剩下：

```text
a[l] + ... + a[r] = prefix[r + 1] - prefix[l]
```

所以这里的两端并不对称：右端要往后跨一步，让 `a[r]` 被算进去；左端不跨，因为要删掉的是 `a[l]` 之前的那些数。

可以用一个反例检验自己有没有真正读对公式。如果误写成 `prefix[r] - prefix[l]`，刚才查询下标 1 到 2 就会得到 `prefix[2] - prefix[1] = 3 - 4 = -1`。它只剩下 `a[1]`，漏掉了 `a[2]`。看到少的恰好是最后一个数，就能追溯到右边累计结果没跨过结束位置。

一个很有帮助的表示法，是把累计结果想成放在数字之间的“分界处”：

```text
prefix[0]   prefix[1]   prefix[2]   prefix[3]   prefix[4]
     |   4   |   -1   |    3    |    2    |
```

你要取哪些数，就找到它们前面的分界和后面的分界，用后者减前者。下标 1 到 2 的数字，前面是分界 1，后面是分界 3，因而计算 `prefix[3] - prefix[1]`。这个图和刚才的公式完全是一件事，只是换了表示方式。

现在看一个关键边界：查询从第一个数开始，即 `l = 0`。这时前面没有任何数字需要删去，于是 `prefix[0]` 必须等于 0：

```text
下标 0 到 2 的和
= prefix[3] - prefix[0]
= 6 - 0
= 6
```

提前存这个 0，是为了让“从开头查”和“从中间查”使用同一条规则。它不是随便补的占位值，而是“取零个数的和”。正因如此，原数组有 `n` 个数，累计数组需要存从 0 到 `n` 这 `n + 1` 个结果。

最小代码就是上述定义的直接翻译：

```python
a = [4, -1, 3, 2]
prefix = [0]

for number in a:
    prefix.append(prefix[-1] + number)

l, r = 1, 2  # 两端都包含
answer = prefix[r + 1] - prefix[l]
print(answer)  # 2
```

`prefix[-1]` 取的是当前最后一个累计结果；加上新数字，就得到多包含一个数的累计结果。查询时只是找到两个分界，再相减。负数会让累计结果下降，但公共开头仍能抵消，因此不影响这个公式。

还要留意：有些教材把 `prefix[i]` 定义成“包含下标 i 的累计和”，那套下标和这里不同。遇到不同公式时，先读它如何定义 `prefix`，不要只比较符号。本轮始终采用“前 k 个数”，因此规则保持一致。

这一模块的理解标准，是你能说出：两个累计结果各包含哪些数，多出来的共同开头是什么，为什么减完恰好留下目标段。如果愿意自检，可以试着解释上面“从下标 0 到 2”的计算为什么不需要特殊分支；暂时不必往二维或其他题型扩展。

## 第 5 轮

**用户：** 直接给我答案，讲讲为什么。

**助手：**

下面直接给完整解法示范。先算出前 `k` 个数的总和，再让这个长度固定的框向右移动：每次减去离开的数，加上进入的数，同时记住遇到的最大总和。

如果对每个片段都重新相加，相邻片段里那些重复出现的数就会被反复计算。这里能省下这些工作，是因为框每次只移动一格：中间的数全部保留，变化的只有两端。这种移动框并维护其中信息的方法，就是**滑动窗口**。

以题目的数组为例，四个长度为 `3` 的片段总和依次是：

```text
[2, 1, 5] → 8
[1, 5, 1] → 8 - 2 + 1 = 7
[5, 1, 3] → 7 - 1 + 3 = 9
[1, 3, 2] → 9 - 5 + 2 = 6
```

所以最大总和是 `9`。

下面是完整的 Python 示例，输入满足题目给定的条件：

```python
def max_window_sum(nums, k):
    current = 0
    for i in range(k):
        current += nums[i]

    best = current

    for right in range(k, len(nums)):
        current += nums[right] - nums[right - k]
        best = max(best, current)

    return best


print(max_window_sum([2, 1, 5, 1, 3, 2], 3))  # 输出 9
```

数组下标从 `0` 开始。`right` 是本次新进入框的数的位置；`right - k` 是刚离开框的数的位置。因此更新后，`current` 仍然恰好是当前连续 `k` 个数的和。

`best` 一开始保存第一个片段的和，之后每移动一次就与新片段的和比较。这样每个合法片段都检查一次，也就不会漏掉最大值。

设数组长度为 `n`。总工作量随 `n` 成正比，时间复杂度记作 `O(n)`；只需要固定几个变量，额外空间记作 `O(1)`。
