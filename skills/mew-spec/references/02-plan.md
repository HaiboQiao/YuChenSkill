# 阶段二：技术设计与 `plan.md`

**输入：** 已批准的 spec、相关代码与既有契约。  
**输出：** 足以定位关键实现决策的 plan，按主文件处理批准。

## 工作流

1. 重新核对 spec 的范围、默认、约束和 AC，优先复用仓库结构与既有接口。
2. 定义本次新增或改变的职责、数据结构、关键接口和依赖；未改变契约引用准确路径与章节。
3. 描述调用顺序与数据流。涉及状态、并发、外部副作用时，明确相关状态转换、完成边界与失败处理。
4. 列出文件组织与重要技术取舍，逐文件步骤留给 task。不为小增量新造抽象层。
5. 核对需求覆盖和上游一致性，写完整后按授权继续或请求整份批准。

## 内容骨架

```markdown
# 功能名称 Plan

## 职责与需求覆盖
说明现有组件、本次增量及对应 F/N/AC；明确依赖方向。

## 关键契约
列出新增或改变的类型、接口及行为；未变部分给出准确引用。

## 调用与状态流程
说明输入经过哪些边界、输出在哪里产生，以及适用的失败/取消路径。

## 文件组织与技术决策
定位新建/修改文件，记录重要选择、理由及实际代价。
```

## 契约最低要求

对新增或改变的关键接口写清：签名或等价协议、输入类型与限制、默认值、输出、错误的传播或表示。仅写方法名称不足以交接；不必粘贴完整实现。

涉及取消和副作用时还要确定：验证/授权/执行顺序，取消信号由谁接收，何时算成功，已发生影响如何报告，是否会重试以及重复执行是否允许。不同阶段共享同一语义，不能在文案层把已成功写入说成已回滚。

可用短契约表表达：

| 接口/阶段 | 输入与限制 | 输出/状态 | 失败与取消 |
|---|---|---|---|
| 本次改变的边界 | 写具体参数及单位，或引用旧契约 | 写调用方可用的结果 | 写传播方式及残留影响 |

## 自检

- 每条需求都能定位负责组件或现有契约；每个新增组件都有本次需求依据。
- 新接口足以独立实现，限制没有混淆对象，失败、取消和状态定义与 spec 一致。
- 依赖清楚、无环；目录、类型与符号命名遵循现有代码，供 task 准确引用。
- 测试替身与真实服务各能证明什么写清，环境缺口没有被设计悄悄消除。
- 发现需求缺口回到 spec；仅实现方式细化留在 plan。没有新分歧时不增加额外审批。
