# 阶段四：验收设计与 `checklist.md`

**输入：** 已批准的 spec、plan、task。  
**输出：** 行为、集成与工程证据各有所指的 checklist，按主文件处理批准。

## 工作流

1. 将每条 AC 映射到至少一项稳定 ID 的清单；覆盖具有验收意义的 N。
2. 从 plan 提取本次关键集成路径，从仓库规则提取适用的工程检查，不重复每个内部实现步骤。
3. 至少设计一个走完用户可见流程的端到端场景及重要边界；纯配置/内容工作使用相应的完整消费或使用流程。
4. 核对必需完成条件、可用环境与缺口。写完整清单、自检，再按授权继续或请求整份批准。

## 内容骨架

```markdown
# 功能名称 Checklist

## 本次完成条件与环境
列出必需项、目标兼容范围、可用环境及未具备条件。

## 用户行为
- [ ] C1（AC1）：在具体条件下执行操作，观察具体结果；验证入口或场景。

## 关键集成
- [ ] C2（相关 AC）：走实际调用路径，确认上下游输入、输出与状态一致；验证场景。

## 工程检查
- [ ] C3：执行仓库已有的适用检查，记录退出结果和统计。

## 端到端
- [ ] C4（相关 AC）：准备环境、完整用户操作、预期反馈与最终状态。
```

章节与条目须替换为本次实际内容。每项标明适用环境及必需/可选性质；初始状态为未执行，批准清单不代表已经通过。

## 证据与状态

- 条目定义聚焦稳定行为，与私有函数和内部文件组织解耦。具体执行入口可引用 task 或证据记录的准确位置，不能只写“运行对应测试”。
- 行为测试证明对应行为；集成场景证明被执行的调用链；编译、测试汇总或静态检查支持各自的工程结论。它们不能单独证明所有公开接口都有真实调用方。
- 确定性服务可验证协议与时序，真实服务验证相应端点；无界面测试不能替代真实终端，已测平台不能外推到未测平台。
- 通过须有足以支持该项的实际证据。未执行、失败、跳过、环境阻塞和待复验保留未勾选并说明原因；跳过不计为通过。
- 后续改变影响某项原证据时改为待复验，保留有日期的历史结果。缺少必需环境时不能静默改为可选或报告全部验收完成。

## 编码前联合核对

确认 F/N→AC→C 覆盖完整，四文档的默认、限制、成功/失败/取消、接口名和依赖相容，每项都有可执行验证。矛盾回到受影响的最早文档处理；没有新的关键分歧，不新增第五次例行审批。
