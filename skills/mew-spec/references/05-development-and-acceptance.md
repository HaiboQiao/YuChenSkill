# 开发与验收

确认四文档已有有效批准，或用户明确授权的流程允许实现后使用。授权来源与范围遵循主文件，不从 Agent 自写“批准”状态推导权限。

## 开发

1. 联合核对四文档关键契约与覆盖，说明当前执行依据；没有新分歧不再请求重复批准。
2. 按 task 依赖实现行为并运行该任务必要验证，检查实际输出后更新任务状态和证据引用。
3. 验证失败先诊断修复，重跑相关检查；范围不变的修复无需重新审批全部文档。新增需求或重要契约变化按主文件的变更分类处理。
4. 关键需求不能确定时提出必要问题，只暂停依赖它的工作，继续不受影响的任务。环境不足先标注未验证，不猜测结果或降低完成条件。
5. 遵循仓库提交与交付约定；外部动作需有相应授权。

## 状态与执行证据

task 集中任务进度，checklist 集中当前验收状态，详细证据集中到仓库已有 verification 或报告位置；没有既有位置时选择一个合适记录位置，不为审批新增系统。

每次执行至少记录：日期、实际代码产物或状态、环境、命令/操作、实际结果、支持的 C/AC ID。已有版本控制时引用真实版本及工作区状态；没有提交时用可核查的产物位置/标识，不能编造提交号。预期结果与实际执行结果分别写。

影响证据的改动发生后，明确受影响 ID 并改为待复验，再执行相应检查。历史通过保留日期与当时产物，不能作为当前改动的证明。纯结果或进度更新不触发需求重批。同步清理当前说明中的旧路径、旧“未运行”文字和互相冲突的完成总结；历史事实保留并标清时点。

## 验收与维护性评审

1. 按 checklist 执行实际场景，核对证据能否支持对应结论；仅测试汇总不足以替代端到端行为。
2. 修复未通过项并复验。检查范围随实际变更、失败与剩余疑点确定；已有检查通过且无新风险时无需反复扩大测试。
3. 交付前评审本次代码：关键输入输出是否清楚，组件结构是否一致，职责是否过度集中，协议差异是否放在适当边界，必要注释是否解释机制。
4. 使用已有格式/静态检查，不强制新增 lint、类型工具或依赖，不设函数行数上限。指出维护问题时引用具体位置与影响；不阻塞当前交付的建议可列后续项。
5. 仓库有阶段学习/复盘要求时按当地规则执行，不把特定教程结构、终端工具或知识库路径推广为所有项目的规则。

## 交付报告

给出用户可见成果、已执行验证及证据链接、未通过/未执行/待复验项与原因。区分“实现完成”“当前环境已测范围”“必需验收仍缺什么”。必需项尚未验证时保持验收未完成；若用户明确调整完成条件，记录依据和剩余范围。不要把修复后尚未运行的预期写成通过。
