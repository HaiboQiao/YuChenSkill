# 阶段一：需求澄清与 `spec.md`

**输入：** 用户想法、真实仓库与现有约束。  
**输出：** 完整 spec，默认请求一次整份批准；授权例外遵循主文件。

## 工作流

1. 确认当前能力、本次要改变的行为与不做的事，避免把参考项目的全部能力变成需求。
2. 只澄清无法从输入与仓库可靠确定、且会改变成功标准的关键问题。可推断的重要假设写明供审查，不反复问已回答的问题。
3. 按实际需要比较可行方案，或说明已选路径的理由。涉及独立子系统时确认交付边界。
4. 提前区分本次必需完成条件、目标兼容范围、当前可用环境和可选验证。真实服务、目标平台或端到端条件不足时列出缺口，不自动降为可选。
5. 写完整文档并自检，再呈现关键决定、假设和验收条件，按已有授权继续或请求整份批准。

## 内容骨架

```markdown
# 功能名称 Spec

## 背景与目标
说明已有能力、要解决的问题和用户将获得的能力。

## 功能需求
- F1: 用明确输入、默认值、输出和边界描述行为。

## 非功能需求与约束
- N1: 本次实际适用的性能、兼容、安全或运行约束。

## 范围与重要假设
明确不做的事；记录影响行为的假设及待确认问题。

## 验收标准与环境
- AC1（F1）: 给定输入与条件，执行操作后观察到的结果。
说明必需环境、可用环境与尚缺条件。
```

骨架提示须替换为本次具体内容；不适用的章节可省略或简述。存在会改变行为的未决关键问题时，明确标为待澄清，不把占位文本当作已完成规格。

## 写作与自检

- 聚焦用户或调用方可观察的行为。保留明确的语言版本、协议、配置格式和平台约束；内部方法名、类型与文件组织留给 plan/task。
- 对涉及状态或副作用的能力，覆盖适用的成功、失败、取消以及已经发生的影响。只有具有实际保证时才承诺回滚。
- 限制必须说明对象、单位、边界与失败结果，例如单次请求参数大小和目标文件大小是不同约束。
- 每条 F 和具有验收意义的 N 至少对应一条 AC；AC 写可观察结果，不只写“测试通过”。
- 检查默认行为、边界、重要假设是否有两种解释；补齐真正缺口，不机械展开未改变的旧需求。

未批准时停在完整 spec，不修改实现。已获有效连续授权时记录依据并进入 plan，不追加逐段确认。
