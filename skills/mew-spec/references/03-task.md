# 阶段三：任务拆解与 `task.md`

**输入：** 已批准的 spec、plan。  
**输出：** 能按依赖实施与验证的任务，按主文件处理批准。

## 粒度与顺序

以一种独立可验证的行为或一个可用契约为任务单位，把实现与必要验证放在同一任务。不同失败边界需要独立检查时可拆分；不要按预计分钟数，把导入、字段、函数壳和断言机械拆成任务。

先列文件操作，再按真实依赖组织任务。无需修改的组件可以验证或引用，不为“每个组件一个任务”制造工作。明确起点、前置条件、完成条件与无环执行顺序；可并行只针对没有冲突的任务。

## 单任务骨架

```markdown
## T1：可交付的行为名称
状态：待开始
覆盖：相关 F/N/AC
文件：仓库相对路径；分别标明新建、修改或验证
依赖：无，或列出任务 ID 与所需结果
契约：plan 中准确的章节/接口引用

步骤：
1. 在明确位置实现本任务行为，说明关键操作。
2. 增加或调整必要验证；低影响可逆修改可使用直接检查。

验证：执行具体入口或人工场景，观察具体结果。
完成条件：行为及必要验证均满足，结果记录可定位。
```

执行所需信息应可定位，允许引用 plan 的明确契约，不重复整段设计。任务单独阅读时应知道要改哪里、依赖什么、去哪里查契约、怎样验证；“其余类似”“按之前方式”不构成有效引用。

## 具体步骤与验证示例

不合格：`实现文件写入，运行对应测试，确认正常。`

合格的任务说明可以是：

> 修改 `src/write_tool.py` 的写入入口，按 plan“写入契约”实现新建及默认拒绝覆盖；新建 `tests/test_write_tool.py` 验证新文件内容、已有文件拒绝后字节不变。依赖 T1 的输入验证结果。在仓库根、项目测试环境运行 `python -m pytest tests/test_write_tool.py -q`，确认这两类场景均被执行并通过。

示例中的路径与入口须替换为真实项目约定。规划的新测试尚不存在时，明确由哪项任务创建；执行时确认入口存在且匹配用例，零匹配、跳过不能作为行为通过。人工验证要写准备环境、输入、操作和预期观察；仅编译或导入不能证明业务行为。

## 自检与维护

- 每个新增/改变的行为有任务覆盖，文件清单与任务正文一致，命名与 plan 一致。
- 步骤无未完成占位或模糊指代；依赖 ID 存在、无环，并且存在可执行起点。
- 每项验证都有可定位入口和预期，涉及外部服务/平台时注明前置条件。
- 不新增无必要的测试或工具；必要检查遵循仓库要求。
- 写完整 task 后按授权继续或请求整份批准。实施期间当前任务进度只在这里维护；有待复验或阻塞时如实标注，不在各文档复制总进度。
