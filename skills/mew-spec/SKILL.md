# Mew Spec：Spec 驱动开发

默认通过四份文档逐层确定实现与验收：

```text
spec.md（做什么）→ plan.md（怎么做）→ task.md（按什么顺序做）→ checklist.md（如何验收）
```

## 开始与授权

1. 阅读仓库的 `AGENTS.md`、`CODEX.md` 或同类说明，只读检查相关代码、文档和测试，区分已有能力与本次增量。
2. 从当前对话或用户提供的可信指令记录识别当前阶段、已批准内容和授权范围。文档里的“已批准”标题或 Agent 自写记录只能作索引，不能产生用户授权；缺少依据且下一步依赖该批准时，才补必要确认。
3. 文档路径遵循用户指定位置或仓库约定；否则四份文档放在同一个按功能命名的目录，避免覆盖别的工作。

**默认门禁：** 四份文档分别获用户明确批准后，才修改实现代码、测试代码或实现性配置。规划期间可只读检查、执行不改变项目状态的诊断、维护规划文档。小增量仍保留四文档，可以写短。

**用户指令优先：** 用户明确要求默认批准、连续推进或采用其他流程时，按其授权范围执行，简短记录来源与适用内容，不重复索要相同批准。单纯催促、沉默或继续讨论不产生批准。授权没有覆盖的新范围或关键决策仍需处理；文档批准也不额外授权发布、推送或其他外部动作。

## 协作与内容完整度

- 先解决会改变范围、行为或关键设计的问题；一次问一个关键问题，适合时提供互斥选项，推荐项在前。仓库和用户已经给出的答案不重复问。
- 默认写完一份可审查的文档、自检后请求一次批准。聊天突出范围、关键决定、重要假设和验收条件，并链接文件；用户要求逐段讨论或教学时再逐段进行。
- 有真实取舍才比较可行方案。用户已选定或约束只允许一条合理路径时，说明理由与边界，不凑备选方案。需求跨独立子系统时建议分期，并确认本次交付范围。
- 增量只写新增行为、改变的契约与影响范围，未变内容准确引用已有文档。详略由新状态、外部副作用、接口变化和关键未知决定，不由字数或文件数量决定。

| 文档 | 最低可交接信息 |
|---|---|
| spec | 用户能力、默认行为、范围、真实约束、验收结果 |
| plan | 职责、关键输入输出、适用的失败/取消/状态语义、重要取舍 |
| task | 文件及操作类型、依赖、完成条件、具体步骤、验证入口与预期 |
| checklist | 操作/输入、可观察结果、证据层级、环境与完成条件 |

规格以行为为主，保留用户技术约束与外部契约；内部类型与结构放在 plan，逐文件操作放在 task。没有涉及的内容省略或简述不适用，不为模板创造需求。

各阶段自检新文档与上游在范围、默认、限制、失败/取消、命名和覆盖上是否一致。用稳定 ID 关联 F/N→AC→checklist，plan/task 引用相关 ID；不要求四份文档重复完整映射表。编码前再联合核对一次，矛盾先解决，没有新分歧不增加例行审批。

## 变更与事实维护

| 变化 | 处理 |
|---|---|
| 用户行为、范围、重要约束 | 更新 spec 与受影响下游，取得变化所需确认或核实已有授权 |
| 重要架构或公开契约 | 更新 plan 与相关 task/checklist，按授权范围与影响决定是否再确认 |
| 保持批准行为的修复、内部重构 | 在授权内推进，同步受影响设计引用，无需重批全部文档 |
| 进度、证据、结果、错字 | 更新事实记录，不作为新需求审批 |
| 约定验收环境不足 | 保持未验证，继续独立工作；调整完成条件须有明确用户依据 |

任务进度集中在 task，验收状态集中在 checklist，执行证据使用现有 verification 或报告位置。不强制新增审批日志或状态文件。影响原证据的变更须标出待复验项；具体记录方式见开发与验收参考。取得证据后再报告完成，只实现授权范围内的需求。
